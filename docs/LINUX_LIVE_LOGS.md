# پایش زندهٔ لاگ لینوکس با یک جمله

در داشبورد، بخش «اقدام با یک جمله»، تجهیز لینوکسی دارای SSH و اعتبارنامهٔ ذخیره‌شده را انتخاب کنید. مثال‌ها:

- «لاگ nginx» یا «لاگ سرویس nginx» — خواندن هم‌زمان فایل‌های واقعی سایت‌ها، journal سرویس و کانتینرهای وب مرتبط؛ نه فقط access.log پیش‌فرض.
- «لاگ سرویس docker» یا «لاگ سرویس my-api» — journal واحد systemd؛ با نام دقیق واحد.
- «لاگ کانتینر my-api» — stdout/stderr همان کانتینر در حال اجرا؛ نه اجرای فرمان داخل کانتینر.
- «لاگ IP 192.0.2.10» — جست‌وجوی دقیق IP در منابع کشف‌شدهٔ journal، فایل‌های لاگ و کانتینرها؛ دیگر فقط journal نیست.
- «لاگ nginx برای IP 192.0.2.10» — فیلتر IP در منبع وب انتخابی.
- «لاگ سرویس my-api شامل «connection refused»» — عبارت literal، نه regex یا فرمان پوسته.
- «لاگ خطاهای سرویس my-api»، «لاگ کرنل» یا «لاگ /var/log/secure».
- «لاگ journal nginx» یا «لاگ unit nginx» — فقط journal همان واحد، اگر عمداً این منبع را می‌خواهید.

بعد از به‌روزرسانی، صفحه را تازه کنید و درخواست پایش جدید بسازید؛ نشست قدیمی یا پیش‌نمایش منقضی خودکار به منبع دیگری تبدیل نمی‌شود. برای تست سایت ابتدا «لاگ nginx» بدون IP را باز کنید، سپس یک درخواست تازه و بدون کش به سایت بفرستید. اگر IP در لاگ با IP مرورگر متفاوت است، پراکسی/CDN/NAT یا قالب ثبت IP را بررسی کنید؛ برنامه IP را حدس نمی‌زند. نام دامنه لزوماً داخل متن access log نیست؛ درخواست فقط با نام دامنه روشن‌سازی می‌خواهد، نه فیلتر ساختگی که همهٔ رویدادها را پنهان کند.

پیش‌نمایش، منبع، فیلتر، تجهیز و کلید SSH را نشان می‌دهد. اولین کلید را با تجهیز تطبیق دهید. دکمهٔ «تأیید و شروع پایش» یک تأیید است؛ قبل از آن هیچ فرمان لاگ روی تجهیز اجرا نمی‌شود (فقط بررسی کلید میزبان پیش از احراز هویت). درخواست مبهم روشن‌سازی می‌خواهد؛ دستورات خام کاربر/AI اجرا نمی‌شوند.

## مسیر اجرا و دسترسی

`intent -> linux.live-logs -> ActionPlan -> preview -> one confirmation -> PolicyGuard -> linux_live_log_query -> Linux SSH connector -> verified source/live session -> audit -> cursor long-poll UI`

- تمرکز فعلی Linux با SSH اصلی است. اپراتور و مدیرِ دارای دسترسی اقدامات می‌توانند پایش خودشان را آغاز کنند؛ مشاهده‌گر یا حساب فاقد بخش، نه. جلسه به کاربر و مالک فضای کاری متصل است؛ شناسهٔ تصادفی به‌تنهایی اجازهٔ خواندن نمی‌دهد.
- ثبت قالب/پلنر/کانکتور واقعی، `intent=execute`، اعتبار پارامترها و ممیزی لازم‌اند. تنظیمات quick-controlled/lab و رفتار سایر دستورات دست‌نخورده‌اند. `linux_read_auth_logs` قدیمی به این جریان جدید هدایت نمی‌شود؛ شناسهٔ صریح کاتالوگ لازم است. مهاجرت دیتابیس لازم نیست.
- کلید SSH در پیش‌نمایش و اتصال واقعی یکسان است؛ کلید تأییدشده ذخیره می‌شود. تغییر کلید، تنظیم اتصال، اعتبارنامه، شرکت، مالکیت یا مسیر VPN دسترسی را متوقف می‌کند. مسیر VPN اعتبارسنجی می‌شود؛ این قابلیت تونل جدید فعال نمی‌کند.
- بعد از long-poll، اعتبار نشست ورود، نقش، مجوزها و تجهیز دوباره بررسی می‌شوند؛ لغو دسترسی نباید متنِ منتظر تحویل را آزاد کند.
- منابع صریح قبلی journal، فایل‌های مشخص auth/secure/syslog/messages/kernel/UFW/nginx/Apache/fail2ban و Docker همچنان پشتیبانی می‌شوند. هیچ مسیر یا فرمان آزاد کاربر/AI اجرا نمی‌شود. فایل باید regular/readable، بدون مسیر traversal و canonical باشد؛ symlink فایل یا پوشه به منبع خارج از مسیر پذیرفته نمی‌شود.
- تشخیص چندمنبعی با Python 3 استاندارد روی تجهیز و یک کانال SSH انجام می‌شود؛ بسته‌ای خودکار نصب نمی‌شود. نبود Python خطای فارسی و مسیر جایگزین انتخاب واحد/کانتینر/فایل صریح دارد. فایل‌های فعال با پسوند `.log` / `_log` و syslog/messages/secure در `/var/log` تا عمق محدود بررسی می‌شوند؛ journal و stdout/stderr کانتینرهای در حال اجرا نیز خوانده می‌شوند. کانتینر وب با نام/تصویر nginx/Apache/httpd یا پورت منتشرشدهٔ 80/443 شناسایی می‌شود، نه حدس نام یک کانتینر. این معیار همهٔ پراکسی‌های سفارشی با پورت داخلی را تضمین نمی‌کند؛ انتخاب کانتینر صریح همچنان موجود است.
- برای Nginx، فرمان ثابت فقط‌خواندنی `nginx -T` در خود تجهیز و کانتینر وب مرتبط اجرا و فقط مقصدهای access_log/error_log **داخل همان فرایند روی تجهیز** استخراج می‌شوند؛ متن کامل تنظیمات، headers، env و اسرار ارسال یا ذخیره نمی‌شود. فقط فایل canonical زیر `/var/log` با نام امن لاگ خوانده می‌شود. مقصد خارج از این محدوده، syslog شبکه‌ای، مسیر متغیر و access_log off با هشدار پوشش گزارش می‌شود، نه تغییر خودکار تنظیمات. داخل کانتینر فقط فرمان‌های ثابت nginx/readlink/test/timeout/tail اجرا می‌شوند؛ shell دلخواه وجود ندارد. دستور `timeout` داخل کانتینر برای دنبالهٔ فایل لازم است؛ نبود ابزار، منبع را شکست‌خورده نشان می‌دهد.
- فقط ID/Names/Image/Ports از Docker درخواست می‌شود؛ env/labels/inspect کامل خوانده نمی‌شود. چند کانتینر مرتبط می‌توانند هم‌زمان پایش شوند؛ هرکدام منبع مجزا دارند. شاخهٔ fallback قدیمی برای پیش‌نمایش‌های ساختاریافتهٔ قدیمی حفظ شده، اما درخواست‌های جدید وب از تشخیص چندمنبعی استفاده می‌کنند، حتی وقتی فایل پیش‌فرض موجود ولی خالی است.

## نمایش و محدودیت‌ها

- اصلاح تجربهٔ پنجره (۲۰۲۶-۱۰-۲۳، فقط محلی): ترتیب رویدادها با شمارهٔ دریافت مشخص است؛ قدیمی‌تر بالا و جدیدتر پایین، مستقل از ساعت دستگاه‌های مختلف. آخرین رویدادِ قابل‌نمایش برچسب دارد و دکمهٔ «جدیدترین لاگ» با پاک‌کردن فیلتر نمایش و پایان مکث به انتهای پنجره می‌رود. هنگام مرور رویدادهای قبلی اسکرول جابه‌جا نمی‌شود؛ شمارندهٔ دریافت‌های ندیده فقط در محدودهٔ پنجرهٔ حافظه است، نه کل تاریخچه.
- توقف واقعی و بستن نمایش جدا هستند: پس از توقف دکمهٔ بستن در بالا و پایین موجود است؛ بستن در حالت دریافت ابتدا توقف واقعی را درخواست می‌کند. شکست توقف، موفقیت ساختگی یا حذف پنجره ایجاد نمی‌کند؛ تلاش دوباره ممکن است. نشست منقضی/ناموجود (۴۰۴) قابل بستن است. پاسخ دیررسِ long-poll نمی‌تواند توقف یا بستن موفق را برگرداند. حذف نمایش در داشبورد شناسهٔ نشست را هم از والد پاک می‌کند تا درخواست بعدی بدون پنجرهٔ قبلی باز شود.
- متن طولانیِ تشخیص منابع از پیش‌نمایش حذف شده؛ خلاصهٔ فقط‌خواندنی/محدودیت زمان و کلید SSH همچنان قبل از یک تأیید دیده می‌شود. هشدار خروج رویدادهای قدیمی جمع‌شونده است، نه حذف یا پنهان‌کردن محدودیت واقعی. صفحهٔ بیرونی هنگام رسیدن به انتهای کنسول موبایل دیگر در اسکرول داخلی حبس نمی‌شود.
- ۵۰ خط اخیر هر منبع، سپس جریان پیوستهٔ SSH. تحویل HTTP با cursor/long-poll بیدارشونده با رویداد است؛ timeout خالی ۱۰ ثانیه و تجمیع کوتاه ۲۰۰ms، نه جمع‌آوری batch ده‌ثانیه‌ای. تأخیر شبکه/نوشتن بافر لاگ منبع جداست؛ SLA سخت realtime وعده داده نمی‌شود. کش مرورگر ممکن است اصلاً درخواستی به سرور نفرستد.
- تشخیص حداکثر ۲۰ ثانیه بودجهٔ فرمان دارد (هر فرمان حداکثر ۴ ثانیه/خروجی محدود)، ۱۲ کانتینر، ۳۲ فایل کشف‌شده، ۶۴ مقصد تنظیم‌شدهٔ Nginx و در مجموع ۴۸ منبع؛ عبور از سقف با هشدار صریح است، نه ادعای پوشش کامل. مقصدهای تنظیم‌شدهٔ canonical که در پیمایش نبودند نیز تا سقف کل افزوده می‌شوند. stdout و stderr کانتینر هر دو لاگ‌اند؛ stderr ابزار journal/tail فقط هشدار تشخیصی است. منبعی که بسته شود جداگانه failed می‌شود و منابع سالم دیگر ادامه می‌دهند؛ نبود هیچ منبع فعال شروع موفق ایجاد نمی‌کند.
- وضعیت، تعداد خوانده‌شده/مطابق و آخرین دریافت هر منبع در API وجود دارد؛ UI منبع، وضعیت و شمارنده را نشان می‌دهد. شمارنده‌ها **سطر لاگ** هستند نه درخواست/حملهٔ یکتا؛ ممکن است یک درخواست در فایل، journal و کانتینر تکرار شود. توقف، فرایندهای محلی collector را می‌بندد؛ فرمان فایل داخل کانتینر نیز timeout مستقل محدود دارد. تغییر/چرخش فایل با tail -F دنبال می‌شود.
- ۵۰۰ رویداد یا ۱MiB برای هر جلسه، حداکثر ۸ جلسهٔ فعال کل و ۲ برای هر کاربر؛ جلسه‌های بسته محدود/منقضی می‌شوند. تا ۳۰ دقیقه؛ ترک صفحه/قطع خواندن پس از حدود ۴۵–۵۰ ثانیه جریان را می‌بندد. پنجرهٔ قدیمی آرشیو نیست و از دست‌رفتن دادهٔ پنجره اعلام می‌شود.
- سقف خط/نرخ ورودی و زمان فرمان/اتصال از حافظه و اتصال رهاشده جلوگیری می‌کند. قطع منبع، نبود ابزار، فایل/واحد/کانتینر ناموجود و نداشتن مجوز جداگانه گزارش می‌شوند. خط بسیار بزرگ یا جریان افراطی ممکن است نیاز به منبع محدودتر داشته باشد.
- متن خام لاگ روی دیسک یا در ActionPlan/audit ذخیره نمی‌شود؛ audit شناسه‌ها، وضعیت و شمارنده‌ها را نگه می‌دارد. فرم پرس‌وجو و نتیجهٔ شروع نشست همچنان در سابقهٔ اقدام وجود دارند؛ رمز/توکن را در عبارت درخواست وارد نکنید.
- رمز/توکن/cookie/authorization/URL credential و بلوک کلید خصوصی متداول پیش از تحویل پوشانده/حذف می‌شوند؛ redaction تضمین کشف همهٔ اسرار آزاد در متن نیست. نمایش React text است، نه HTML؛ کنترل‌های ترمینال و جهت مخرب حذف می‌شوند.
- جست‌وجوی داخل پنجره، مکث/ادامهٔ نمایش، توقف واقعی پایش، شمارنده‌های ورودی/مطابق، زمان تجهیز یا زمان دریافت با برچسب، هشدار پوشش و طراحی RTL روشن/تیره برای موبایل/دسکتاپ وجود دارد. مکث نمایش دریافت را قطع نمی‌کند.
- نبود رویداد، سلامت یا نبود حمله را ثابت نمی‌کند. فقط چیزی دیده می‌شود که سرویس واقعاً لاگ می‌کند و حساب SSH اجازهٔ خواندنش را دارد. حساب محدود پوشش کامل سیستم ندارد؛ sudo فقط بدون رمز امتحان می‌شود و سطح دسترسی تجهیز تغییر نمی‌کند. خطاهای فایل/Docker از الگوی متن تشخیص داده می‌شوند؛ اولویت journal دقیقاً از دستگاه است.
- جلسه‌ها در حافظهٔ یک API هستند؛ restart/deploy جلسه را می‌بندد. برای چند replica به sticky routing یا broker جلسه نیاز است؛ قابلیت فعلی آن را ادعا نمی‌کند.

## اعتبارسنجی

- `backend/test/linux-live-log-query.test.mjs`: intent فارسی/انگلیسی، ابهام، shell/path/option injection، IP دقیق IPv4/IPv6، متن literal، شدت، redaction و تشخیص کانتینر یکتا/کامل.
- `backend/test/linux-live-log-api.integration.test.mjs`: PostgreSQL ایزوله + SSH واقعی آزمایشی + HTTP واقعی؛ مسیر کامل کاتالوگ/preview/یک تأیید/PolicyGuard/کانکتور، تحویل رویداد مرتبط، scope، CSRF، سقف حافظه، توقف، منبع غیرقابل‌خواندن، کلید متفاوت، لغو مجوز حین long-poll، IP در فایل vhost و کانتینر، شکست جزئی/کامل و جداسازی privacy بین منابع.
- `backend/test/linux-live-log-collector.test.mjs`: اجرای واقعی Python/فرایندهای tail روی فایل‌های مصنوعی موقت؛ فایل پیش‌فرض خالی، vhost، مسیر تنظیم‌شده، فایل کانتینر، stdout/stderr، journal، عدم خروج تنظیمات حساس، رد symlink، درخواست HTTP تازه، rotation و خاتمهٔ collector. فایل‌ها و سرویس‌های واقعی مشتری در این تست خوانده نمی‌شوند.
- `scripts/qa/capture-linux-live-logs.mjs`: فقط دادهٔ مصنوعی با APIهای intercept‌شده؛ هر دو تم در ۱۴۴۰/۳۹۰/۳۲۰px، preview بدون اجرا، یک تأیید، HTML بی‌اثر، ترتیب دریافت با ساعت‌های متفاوت، اسکرول/دریافت ندیده، برگشت به جدیدترین از مکث/فیلتر، عبور از ۵۰۰ رویداد، پاسخ دیررس پس از توقف، بستن/بازکردن مجدد و خطای توقف/تلاش دوباره. برای دکمهٔ تأییدِ پایین پیش‌نمایش در عرض باریک، اسکرول واقعی به مرکز انجام می‌شود تا نوار ثابت پایین آن را نپوشاند.
- پذیرش مجاز ۲۰۲۶-۱۰-۲۱ روی یک دارایی لینوکسی ثبت‌شده: درخواست HTTP عادی با شناسهٔ موقت، پاسخ ۲۰۰ و دریافت لاگ همان درخواست از API واقعی در حدود ۵۲۲ms. بدون نگهداری متن/تصویر مشتری؛ نشست ورود موقت حذف و پایش متوقف شد. این تأیید یک دارایی/منبع است، نه همهٔ توزیع‌ها و پیکربندی‌ها.
- اصلاح ۲۰۲۶-۱۰-۲۲: ۷ تست نهایی query/SSH+PostgreSQL API/Python+tail+HTTP+rotation و ۳۳ رگرسیون، ۲۱ تست ظاهر/استقرار و بررسی‌های کاتالوگ/UTF-8/Compose/CI پاس شدند؛ نسخهٔ محلی API و web بازسازی و ۱۸ تصویر مصنوعی هر دو تم در سه عرض بررسی شد. این‌ها پذیرش **دارایی واقعی ۱۱۶** نیستند؛ اجازهٔ تازهٔ نشست تست هنوز پاسخ داده نشده و اجازهٔ یک‌بارهٔ قبلی برای دسترسی به اسرار دوباره استفاده نشده است. هیچ تنظیم لاگ مشتری تغییر نکرده و پوش/استقرار production انجام نشده است.

قفل advisory اجرای اقدام در محیط تست نیز اکنون همان `TEST_DATABASE_URL` اعتبارسنجی‌شدهٔ Prisma را استفاده می‌کند؛ production همچنان `DATABASE_URL` قبلی را دارد. این اصلاح مانع تماس تست کامل با دیتابیس واقعی می‌شود.

مراجع رفتار منابع: [systemd journalctl](https://www.freedesktop.org/software/systemd/man/255/journalctl.html) و [Docker container logs](https://docs.docker.com/reference/cli/docker/container/logs/).
