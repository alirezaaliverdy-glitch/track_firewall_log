# Split-route VPN connections

Open Network Lab > VPN, or `/firewall/tools/vpn` locally. Administrators can save an encrypted WireGuard or L2TP/IPsec PSK profile, review its exact private destination networks, and confirm Connect. Adding a profile never connects automatically. Connect/disconnect require the current profile revision, preventing confirmation of silently changed settings; mutations on one profile are serialized. After confirmed Connect, server-owned durable intent keeps this connection requested across API/helper/host restarts. Confirmed Disconnect cancels that intent, even while the helper is offline or recovery is in flight. This supersedes the former explicit-reconnect-after-recreation behavior.

## Persistent connection and recovery (2026-10-18)

The encrypted profile envelope stores a server-only `connectionIntent` marker; client-supplied markers are ignored. No schema migration, new credential store, plaintext persistent key file or new package is required. Existing disconnected profiles are not auto-activated. A pre-existing managed connected/waiting/stale legacy tunnel is adopted only when actually observed. For a legacy profile whose runtime was already lost before intent could be recorded, the administrator must confirm Connect once; the application cannot safely infer which saved profiles were intended to remain active.

The API worker starts independently of browser tabs and checks every15 seconds. It pages at most64 active-owner profiles per cycle and revalidates encrypted configuration, private routes and asset conflicts before recovery. Transient failures retain connected intent and retry with capped backoff (5,10,20,…300 seconds; actual attempts occur on worker ticks). Credentials/keys are not retained in the bounded retry map. Repeated identical failures do not flood audit. Failed PPP authentication is persisted as an error and pauses automatic login attempts, including after API restart, to prevent account lockout; correct credentials through explicit Disconnect/edit/Connect. This is a safety pause, not an automatic user disconnect.

WireGuard retains its25-second keepalive and normally handles transport loss itself. A stale/waiting link refreshes the endpoint's IPv4 DNS resolution and keepalive without destroying keys, interface or selected routes. A lost interface or failed PPP/IPsec session is rebuilt through a fixed recovery handler. Owned unreachable routes remain during an in-process recovery/failure and are removed by manual Disconnect; default routes and DNS are not modified. Numeric `ip -j -N` output is required: protocol186 otherwise appears as `bgp`, and numeric unreachable type is7. Startup cleanup is restricted to owned-interface routes or the exact guarded route type/metric, not every route with protocol186. Helper recreation still has a short recovery interval; this is not zero-downtime networking or permanent fail-closed routing across namespace destruction.

Status polling no longer terminates PPP/IPsec processes. Health/status reads remain available during serialized long-running connection mutations. A pending manual stop wins over an already-running auto-recovery and is rechecked both before and after helper invocation. UI shows persistent intent separately from actual tunnel state, retry time or credential attention; cancellation remains available while the helper is unavailable. Configuration-based revisions remain stable across background error/timestamp updates.

An internet outage, powered-off endpoint, revoked/expired account, routing conflict or missing kernel support cannot be eliminated by software. These states stay visible and are not labeled connected. The current local saved profile was already disconnected with `VPN_ASSET_ROUTE_CONFLICT` while the camera/NVR subnet is used directly; this task does not bypass that guard, rebind camera assets or activate it automatically.

## Proposed next protocol (research, not implemented)

Recommended next addition: **OpenVPN**, with a safe `.ovpn` importer and the same explicit private-destination routing model. Official clients cover the major desktop/mobile platforms, profiles can be imported from files, and the protocol supports TCP or UDP. Server certificate/CA provisioning remains an administrator task; easy client import does not remove that prerequisite. MikroTik supports OpenVPN but documents compatibility limitations, so certificates/ciphers/transport must be tested against the target RouterOS release. An implementation must reject arbitrary script/plugin/include/file-path directives, validate server identity, ignore pushed default/DNS routes and never execute imported hooks.

For very small customers without a configurable router, a managed on-site connector or **Tailscale subnet router** can be a more approachable onboarding architecture. Tailscale is a managed overlay using WireGuard, not a new VPN protocol. Cameras that cannot run the client still require a reachable always-on gateway/connector inside their LAN; installing only the viewer on a remote phone is insufficient. Subnet routing and exit nodes serve different purposes; do not enable exit-node/full-internet routing. Accounts, access policy, third-party coordination/relay dependency and commercial terms require a separate product decision. No Tailscale account/agent/service or OpenVPN dependency was installed or activated by this task.

## Destination networks, not full-tunnel internet

Enter private IPv4 CIDRs, such as `192.168.18.0/24` for the supplied camera LAN. Up to eight networks per profile are accepted, between `/16` and `/32`. Public networks, `0.0.0.0/0`, IPv6, overlapping active VPN destinations, locally connected Docker/database networks and a VPN endpoint inside its own selected range are rejected. WireGuard AllowedIPs is generated from these destinations only. Tunnel addressing is installed as `/32` without an implicit subnet route. No wg-quick hooks, default-route replacement or application DNS change is supported. The helper verifies the default route before/after connection.

Select Direct network or a named VPN when registering a device, manually adding a camera/NVR or discovering cameras. The selection is persisted; the backend checks workspace ownership and that the destination falls inside that profile's ranges. Saving an offline profile or unverified asset is allowed; testing, discovery and camera viewing require a connected selected VPN and the matching actual route. Existing camera routes can be edited in its details, and device routes in its registration/edit flow. A profile bound to assets cannot be deleted or edited to exclude those assets. A new VPN route that would divert an asset registered for a different access path is rejected. Shared namespace routing means overlapping sites are not independent per-device networks.

The API's SSH, REST, SNMP and camera RTSP/ONVIF traffic to selected destinations uses the same container's exact routes; other traffic follows its existing routes. Camera WS-Discovery multicast normally does not cross a routed VPN; use bounded unicast discovery or add the private IP manually. A live handshake is not proof that a particular camera account/service is reachable: use the IP/port test, then the normal device connection test.

Routes are shared by the application API network namespace, not independently isolated per workspace. Profiles/credentials/operations remain workspace-scoped and admin-managed. Two tenants/sites with the same private addressing cannot use overlapping routes simultaneously. The VPN server must allow the client's address and route/forward the remote LAN; the app cannot change that server automatically. No NAT or LAN forwarding is added to the host.

## WireGuard

Enter endpoint/UDP port, the client's private key and assigned tunnel IPv4 address, the server's public key and optional peer PSK. Alternatively import a single-peer `.conf` in the browser; review the fields and destination networks. DNS, public AllowedIPs and file routing instructions are not applied, and command hooks are rejected. A full-tunnel file such as the operator's supplied sample imports connection fields but clears destination ranges: enter the explicit private LAN (for example `192.168.18.0/24`) before saving. No hidden default LAN is retained. The file remains local to the browser until the administrator saves the validated fields; it is not committed or copied into source. Secret values are never returned by the inventory API and remain blank on edit; blank secret fields keep the existing value. Connection state distinguishes waiting for an actual handshake, connected, stale, failed and disconnected. Keepalive is 25 seconds; MTU defaults to 1420 and can be imported/edited between 1280 and 1420 (the supplied sample uses 1380). Up to 32 profiles can be stored per workspace and four tunnels used simultaneously; active destinations and tunnel addresses must be distinct.

## L2TP/IPsec

The implementation uses IKEv1 Main Mode with PSK, IPsec transport/NAT-T and L2TP with PPP/MSCHAPv2. Plain L2TP, PAP, EAP, aggressive mode and weak DH groups are not supported. Configure the VPN server to accept AES256/SHA256/MODP2048 or AES128/SHA1/MODP2048 for IKE, and AES256/SHA256 or AES128/SHA1 for ESP. Enter the VPN username/password and IPsec PSK in separate fields. PPP does not add a default route or peer DNS. Only one L2TP connection is supported concurrently, among at most four total tunnels.

The L2TP UDP/1701 output guard accepts only IPsec-protected packets to that VPN endpoint; it rejects plaintext fallback. Selected destination routes also have a managed unreachable fallback while the tunnel is active, so loss of its interface cannot silently divert those destinations through normal routing. Explicit disconnect removes only owned VPN routes/rules/links and leaves other networks/default routes intact.

## Container deployment and trust boundary

The user explicitly approved the dedicated VPN helper's root user, NET_ADMIN and `/dev/ppp` access. The API itself stays non-root without NET_ADMIN. `firewall-vpn` shares only the API container network namespace (`network_mode: service:firewall-api`), never host networking, host PID namespace, a Docker socket or a privileged container. Control uses a UID-1000-only Unix socket volume; there is no published control port. Config files containing secrets use a private tmpfs and daemon output is discarded or reduced to fixed error codes. Persistent profile secrets use the existing encrypted credential service and audits exclude them.

Docker's Linux kernel must support WireGuard and PPP, and the Docker host must expose `/dev/ppp`. PPP asynchronous or PPPoL2TP support must also be active: a generic `/dev/ppp` node alone is insufficient. The helper exposes this readiness and fails before dialing when the required drivers are absent. Linux administrators provision kernel support outside this application; no host module loading, broad capability escalation or default network reconfiguration is automatic. The API must already have permitted outbound access to the VPN server (WireGuard UDP port, or IPsec UDP500/4500); the helper does not broaden an intentionally internal-only API network. Local Docker Desktop support must be verified rather than assumed.

Validation on 2026-10-13: the local Docker Desktop kernel successfully completed a real WireGuard handshake and private TCP test while preserving default routing and DNS. Real IPsec transport negotiation and protected L2TP control packets were also observed in the isolated fixture, but complete PPP login/private-host access could not pass because its PPP async/L2TP drivers are inactive. The end-to-end L2TP test is explicitly skipped on that host, not counted as passed. No host kernel module or broader capability was enabled; full L2TP verification still requires a suitably provisioned Linux/Docker host.

Both Compose paths include the helper. Production/root Compose supports WireGuard without requiring a host PPP device. To enable L2TP on a provisioned Linux host, include `-f docker-compose.vpn-l2tp.yml` after the normal Compose files; this adds only the approved `/dev/ppp` mapping. The local firewall Compose retains the previously approved device mapping. No host kernel modification is automatic. Scoped API rebuild recreates the helper against the new API namespace. A stopped API must not leave a helper attached to an old namespace.

The additive transactional `20261013160000_split_vpn` migration requires schema CREATE and AppUser(id) REFERENCES. `20261013170000_vpn_asset_binding` adds the nullable CameraDevice relation and a separate VpnDeviceBinding table; it does not ALTER the legacy Device table because production may have a different table owner. The deploy preflight checks existing CameraDevice ownership and VpnConnection reference permissions, and allows both tables to be created by earlier migrations in the same release. The existing narrow `prepare-camera-migration.sql` helper grants AppUser ID reference permission without changing table ownership. Validate normal and L2TP override Compose separately before rollout; no production deployment has been performed by this task.
