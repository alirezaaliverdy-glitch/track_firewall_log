# Camera previews and NVR channel control

## Periodic identification images

Each camera card shows a small real JPEG for its selected channel/profile; clicking it opens the existing live view. Requests start lazily when a card is first approached, then refresh every three hours while that page is visible. Returning from a hidden page checks the due time. No continuous live stream is opened by the inventory grid. Source/channel changes remount the preview so an old channel is not mislabeled.

The authenticated thumbnail endpoint uses the existing pinned HTTP snapshot/RTSP fallback, then a bounded local FFmpeg decoder (480x270 maximum, 128 KiB output, JPEG dimension/input checks, six-second resize deadline). Two thumbnail acquisitions run concurrently at most. The server rechecks workspace/company/profile and VPN access before using cached bytes and ownership/config revision before returning them. Browser/native requests carry the existing login; responses are private/no-store, with actual acquisition time and stale/refresh metadata. No public camera URL or credential reaches the browser.

Images are memory-only: 64 MiB / 512 entries globally, one entry per owner/camera/profile, three-hour freshness and five-minute failure backoff. A failed refresh can return an explicitly stale previous image; no image produces a clear placeholder, not a fabricated frame. Retained server entries expire after 24 hours; idle expiry runs every minute. Changes invalidate revisions; deletion clears its entries. Browser object URLs are revoked on replacement/unmount. Restart/eviction can cause an earlier new acquisition; there is no permanent file/history or database migration. Initial viewport-only reset behavior was corrected so scrolling does not discard already-loaded card images.

## Real recorder-channel enable/disable

The operator clarified that this means the NVR input channel, **not camera power**. Open the NVR workspace's **Channel control / کنترل کانال‌ها** tab. It reads actual configured channels, including disabled entries, with their names/addresses/states. Operators/admins can request a preview, then explicitly confirm once; viewers only read. Disabling may interrupt incoming video/new recording on that recorder. Existing footage is not deleted and direct camera access/power remain unchanged.

The registered `appweb.nvr.channel_enabled` camera template uses the compatible AppWeb decoder configuration interface. The bounded legacy DES envelope codec is for vendor compatibility only, not EOSNET secret storage. Full decoder settings/accounts stay server-side; only sanitized channel metadata and a revision hash are public. Preview stores the selected index, previous/desired state and full-config hash, never the decoder account/config. Execution re-reads the configuration, rejects stale/missing/unchanged channels, changes exactly one boolean Enable field in the preserved configuration, and performs a fixed encrypted PUT. Success requires a real connector invocation, explicit acknowledgement and a full read-back matching the expected configuration, with PolicyGuard, one-use execution and audit intact. An acknowledgement without the actual change fails verification. Disabled entries remain selectable for restoration.

Unsupported/non-AppWeb firmware has no guessed control or substitute power/recording command. GET capability/schema does not guarantee that firmware/account accepts PUT; real write rejection remains an explicit failed audited action. The actual customer recorder did not answer the read-only LAN panel check during this task. No customer channel was disabled/enabled as a test, so hardware/firmware acceptance remains unverified until an operator performs an explicitly previewed change on a reachable supported device.

Regression coverage includes isolated PostgreSQL/HTTP/JPEG fixtures, encrypted-config round trips, cache TTL/backoff/limits, tenant/viewer/company/profile checks, stale preview/no-confirm/replay denial, field preservation, acknowledgement-only failure and restoration. Synthetic browser suites cover both themes at 1440/390/320px, timestamp refresh/stale handling and channel preview/confirmation/viewer/unsupported flows. Their test-pattern images are not customer footage. CI installs FFmpeg and runs the compiled media/control fixtures after backend build/migrations. No protected Linux/MikroTik policy, schema, device-power operation, push or production rollout is part of this change.
