# Page-level user access

Settings → Users → create/edit account now separates role from visible pages. Use **Cameras & VPN only** to select just those two pages. At least one page is required. Viewer and operator selections are editable; admin intentionally retains full control. Viewer remains read-only except permitted community participation; VPN administration still requires the existing admin role. Page visibility does not grant execution rights or bypass PolicyGuard, confirmation, connector checks or audit.

The existing `AppUser.allowedSections` string array stores validated `page:<feature-key>` grants; no migration is needed. Twenty-three selectable pages cover every currently visible navigation leaf and monitoring. Camera access includes its NVR workspace and NVR registration, not general device management or CLI. VPN is independent of the network lab. Restricted group labels land on the first allowed child; a single child is labeled directly. Sidebar, mobile navigation, account shortcuts, contextual links, fallback navigation and direct routes respect the same selection. Unselected settings/community are not implicit exceptions. The client filters server navigation again to handle stale/over-broad responses safely.

API authorization is server-side. Page-owned endpoints require their page grant, with explicit shared read dependencies for the selected page (for example dashboard aggregates and company lookup). Those dependencies do not expose a sibling navigation page or authorize its mutations. Unclassified API endpoints fail closed for nonadmins; auth/health/filtered product metadata are common infrastructure. Role, workspace scoping, CSRF and existing mutation permissions remain independent checks. Access changes invalidate all target-user sessions transactionally; the user must sign in again.

Compatibility: old unprefixed coarse operator grants expand to their previous page families plus legacy common settings/community. Old viewers previously had all pages irrespective of stored coarse grants, so their existing effective access is preserved until the manager saves an explicit page selection. This avoids silently removing existing customer access during deployment. Editing/saving replaces the legacy data with explicit page grants. New accounts default to only Dashboard in the editor. Unknown grants and empty selections are rejected.

The dependency-free web/API contract is intentionally mirrored; `backend/test/page-access.test.ts` asserts exact source parity and visible-feature coverage. `page-access-api.test.ts` uses disposable PostgreSQL to verify persistence, API denials, viewer read-only, encoded paths, navigation and session revocation. `scripts/qa/capture-page-access.mjs` exercises desktop/mobile/320px dark/light settings, restricted navigation, stale menus, fallback menus and direct routes using intercepted synthetic APIs only.

No production push or customer-account permission change is part of this local implementation task.
