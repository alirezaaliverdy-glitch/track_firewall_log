# راهنمای اتصال ESXi

در «دارایی‌ها ← ثبت دستگاه»، VMware ESXi را انتخاب کنید. اکنون SSH و API هر دو قابل انتخاب هستند. ارتباط از **سرور بک‌اند برنامه** برقرار می‌شود؛ دسترسی لپ‌تاپ به‌تنهایی کافی نیست. اینترنت لازم نیست، ولی مسیر شبکه به هاست ضروری است.

## اتصال SSH

1. وارد Host Client در آدرس `https://<ESXi>/ui` شوید.
2. در **Manage → Services** سرویس **TSM-SSH** را Start کنید. برای SSH به فعال‌کردن سرویس محلی TSM نیازی نیست.
3. در **Manage → Security & Users → Users** برای حساب اختصاصی اتصال، Shell Access را فعال کنید و مجوزهای لازم برای خواندن اطلاعات هاست را بدهید.
4. مسیر شبکه و قوانین SSH Server را فقط برای IP مبدأ بک‌اند برنامه مجاز کنید. اگر NAT دارید، IP واقعی مبدأ را در نظر بگیرید. سرویس را روی اینترنت عمومی باز نگذارید.
5. اثر انگشت **کلید RSA هاست** را از کنسول معتبر یا مدیر هاست دریافت کنید:

   ```sh
   /usr/lib/vmware/openssh/bin/ssh-keygen -l -f /etc/ssh/ssh_host_rsa_key.pub -E sha256
   ```

   این دستور را داخل Shell خود ESXi اجرا کنید، نه در PowerShell ویندوز. مسیر کامل جلوی خطای `ssh-keygen: not found` را می‌گیرد؛ فرمان فقط کلید عمومی موجود را می‌خواند و چیزی را تغییر نمی‌دهد. در فرم ثبت یا ویرایش دارایی، کنار فیلد اثر انگشت، راهنمای «چطور اثر انگشت را بگیرم؟» و دکمهٔ «کپی دستور» موجود است.

   در خروجی‌ای مانند `3072 SHA256:… root@esxi (RSA)`، فقط بخش `SHA256:…` لازم است؛ `3072` طول کلید است و نام هاست و `(RSA)` اطلاعات جانبی‌اند. مقدار نمونه را وارد نکنید؛ اثر انگشت واقعی هاست خود را از مسیر مورد اعتماد بگیرید. این شناسه رمز عبور نیست؛ برای تأیید هویت سرور و جلوگیری از اتصال به سرور اشتباه استفاده می‌شود. گواهی Certificates در پنل HTTPS با کلید SSH متفاوت است.

   فقط مقدار `SHA256:...` را در فرم برنامه وارد کنید، نه کل خروجی فرمان. اگر نسخهٔ ssh-keygen هاست گزینهٔ `-E` ندارد، مدیر می‌تواند **کلید عمومی** را از مسیر مورد اعتماد دریافت کند و با ssh-keygen جدید همین اثر انگشت را محاسبه کند. کلید خصوصی هاست را منتقل نکنید. ssh-keyscan به‌تنهایی تأیید هویت هاست نیست.
6. در برنامه روش **SSH هاست ESXi**، پورت ثبت‌شده (معمولاً ۲۲) و اعتبارنامهٔ رمز عبور یا کلید خصوصی کاربر را انتخاب کنید؛ سپس تست اتصال و ثبت را انجام دهید.

برنامه از RSA-SHA2 استفاده می‌کند؛ به الگوریتم قدیمی SHA-1 ssh-rsa عقب‌گرد نمی‌کند. تغییر اثر انگشت باعث رد اتصال می‌شود؛ ابتدا علت تغییر را با مدیر بررسی کنید. نشست احراز‌شده بین جمع‌آوری و پایش مشترک است؛ keepalive دارد و در قطع ارتباط با تأخیر افزایشی دوباره وصل می‌شود. در تغییر مشخصات اتصال، نشست متعلق به مشخصات قبلی برای هاست جدید استفاده نمی‌شود.

SSH اطلاعات واقعی خودِ هاست را می‌خواند: نسخه/build، مدل/سریال، ظرفیت و مصرف CPU/RAM، حالت Maintenance، دیتاستور، NIC و شمارندهٔ ترافیک، VMkernel، vSwitch، port group/VLAN، سرویس‌ها، DNS/NTP، کنترلر ذخیره‌سازی و قوانین فایروال. بعضی فرمان‌ها به نسخه و مجوز حساب وابسته‌اند؛ اطلاعات ناموجود، خروجی نامعتبر یا جمع‌آوری ناقص «نامشخص/دریافت نشده» می‌مانند، نه صفر یا سالم. سلامت کامل سخت‌افزار و تعداد VM در SSH فعلاً دریافت نمی‌شوند. تنظیم بودن NTP به معنی تأیید همگام‌سازی ساعت نیست.

در **دارایی‌ها ← انتخاب ESXi ← نمای کلی**، نمودارهای مشترک و پنل اختصاصی هاست را می‌بینید. جزئیات شبکه، سرویس و ذخیره‌سازی جدا و جمع‌شونده‌اند. «جمع‌آوری جدید» آخرین داده را به‌روز می‌کند. برای نمودار ترافیک حداقل دو نمونهٔ معتبر از همان کارت شبکه لازم است؛ شمارندهٔ بایت، نرخ لحظه‌ای نیست. این جمع‌آوری از همان نشست SSH مشترک استفاده می‌کند و سقف زمانی ۳۰ ثانیه دارد؛ حداکثر ۱۶ کارت فیزیکی و ۱۰۰ ردیف هر فهرست خوانده می‌شوند. فهرست ناقص به‌عنوان پوشش کامل نشان داده نمی‌شود.

برای تغییر تنظیمات، **تنظیم اتصال API** را باز و روش API را تست کنید؛ سپس در مرکز اقدامات، هاست را انتخاب کنید. عملیات موجود: ورود/خروج نگهداری، شروع/توقف سرویس مجاز و تنظیم NTP. اجرای واقعی فقط بعد از پیش‌نمایش، تأیید و بررسی مجدد وضعیت انجام می‌شود. عملیات تغییردهنده روی اتصال SSH، تغییر شبکه/DNS/دیسک/حساب، reboot و مدیریت VM هنوز پیاده نشده‌اند؛ برنامه ادعای مدیریت همهٔ قابلیت‌های ESXi ندارد.

فعال‌ماندن SSH و شروع خودکار بعد از reboot باید با سیاست امنیتی شرکت سازگار باشد. Broadcom استفاده از Shell را عمدتاً برای عیب‌یابی توصیه می‌کند؛ برای مدیریت مستمر و اطلاعات کامل‌تر API را ترجیح دهید.

## اتصال API هاست مستقل

- برنامه از SOAP در `https://<ESXi>:443/sdk` استفاده می‌کند؛ این API مربوط به خود هاست مستقل است، نه REST API مخصوص vCenter.
- روی هاست با سرویس مدیریتی سالم، معمولاً نصب افزونه/Agent یا فعال‌کردن SSH لازم نیست. از بک‌اند، مسیر مدیریت VMkernel و پورت HTTPS باید در دسترس باشد.
- حساب اختصاصی با مجوز مشاهدهٔ منابع موردنیاز بسازید. برای تغییرات، فقط مجوز همان عملیات را اضافه کنید؛ صرفاً موفق‌شدن ورود به معنی اجازهٔ تمام عملیات نیست.
- گواهی TLS و نام DNS/IP باید منطبق و قابل اعتماد باشند. برای گواهی خودامضا، پس از تأیید مستقل هویت هاست، PEM معتبر را در فیلد گواهی برنامه وارد کنید. برنامه TLS و تطبیق نام هاست را غیرفعال نمی‌کند؛ اگر گواهی IP را پوشش نمی‌دهد، از DNS مطابق SAN یا گواهی اصلاح‌شده استفاده کنید.
- در فرم روش **API هاست ESXi**، نام/IP، پورت HTTPS و نام کاربری/رمز عبور را وارد کنید و تست بگیرید. آدرس فقط هاست است؛ `/sdk` را برنامه اضافه می‌کند.
- Lockdown Mode ممکن است اتصال مستقیم را محدود کند؛ مجوز حساب استثنا را طبق سیاست مدیر تنظیم کنید، نه خاموش‌کردن عمومی کنترل امنیتی.
- نوع لایسنس و نسخه می‌تواند عملیات API را محدود کند؛ به‌ویژه Free Hypervisor ممکن است فقط دادهٔ خواندنی بدهد.

## خطاهای متداول

| نشانه | بررسی |
| --- | --- |
| Timeout / Connection refused | مسیر از بک‌اند، پورت درست، TSM-SSH یا HTTPS و قوانین مبدأ |
| رد نام کاربری/رمز | اعتبارنامه، وضعیت حساب و Shell Access در SSH |
| رد کلید هاست | اثر انگشت RSA را مستقل تأیید کنید؛ بررسی را دور نزنید |
| خطای TLS | CA معتبر و SAN مطابق نام/IP |
| اطلاعات ناقص SSH | مجوز ESXCLI و پشتیبانی فرمان در نسخهٔ هاست |
| عملیات API رد شد | نقش حساب، نوع لایسنس و وضعیت هاست؛ تکرار کورکورانه نکنید |

اگر سرور فقط `publickey,keyboard-interactive` را اعلام می‌کند، کانکتور برنامه اکنون چالش رمزی PAM را هم پشتیبانی می‌کند. این روش، مجوزهای خود ESXi را دور نمی‌زند. اگر MobaXterm پس از دریافت رمز `Access denied` می‌دهد، باید وضعیت رمز/قفل حساب، Shell Access و مجوز حساب روی Host بررسی شود؛ صرفاً تغییر کلاینت کافی نیست. [راهنمای Shell Access](https://knowledge.broadcom.com/external/article/426814/unable-to-access-ssh-on-some-esxi-hosts.html).

ورود موفق به Host Client الزاماً مجوز ورود به Shell نیست. طبق [مستندات رسمی حساب POSIX](https://developer.broadcom.com/xapis/vsphere-web-services-api/latest/vim.host.LocalAccountManager.PosixAccountSpecification.html)، نقش Administrator روی ریشهٔ موجودی و نبود نقش غیرمدیر روی دیگر اشیا در مجوز Shell مؤثر است؛ نسخه‌های جدیدتر مجوز Shell Access جداگانه هم دارند. نقش‌هایی مانند `No Trusted Infrastructure administrator` را معادل مجوز ورود SSH فرض نکنید. در پنل‌های قدیمی که گزینهٔ Shell Access ندارند، مدیر باید نقش و محدودیت حساب را بررسی کند. تغییر نقش به Administrator دسترسی را افزایش می‌دهد و نیازمند تأیید جداگانه است؛ فایل خودکار `access.conf` را برای دورزدن محدودیت ویرایش نکنید.

تست‌های خودکار شامل handshake واقعی روی SSH آزمایشی با password و keyboard-interactive، رد کلید متفاوت، استفاده مجدد از نشست، parser، محدودیت حجم/زمان و تفکیک API/SSH هستند. ورود و بررسی خواندنی Host Client روی ESXi 7.0 U3 با گواهی تأییدشده انجام شده؛ ورود موفق SSH، جمع‌آوری واقعی و عملیات تغییردهنده هنوز تأیید نشده‌اند. پذیرش نهایی باید روی نسخهٔ واقعی شما انجام شود.
